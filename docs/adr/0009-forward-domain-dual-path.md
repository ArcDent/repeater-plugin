# 转发域并入本插件：自动掷骰与请求转发双路径并存

## Context

本插件原有两个行为域（**复读**、**表情回应**），现要并入部署在 arclinux 上的 `papaya0481/maibot-ForwardMessagesAuto-plugin`（v0.2.12）的跨群转发能力。用户口径（阶段一澄清）：

- 源群白名单里出现**合并转发**后，**自动转发**路径按**转发权重**对每个**目标群**独立掷骰决定是否转发，不经过 LLM 判断——与本插件复读/表情回应两域「纯规则 + 概率」的哲学一致；
- 群友在对话中要求转发（如「帮我转给 X 群」）是既有的使用习惯，这条**请求转发**路径继续保留原插件的完整链路（源群强制触发 Planner、**查看资格**、一次性授权、顺序投递），不掷骰；
- 转发成功后复用本插件的上下文注入能力：目标群注入转发内容，源群注入行为留痕；**自动转发**额外触发一次目标群 Planner 并软约束其说一句话。

原插件的完整链路（`forward_messages_auto/` 下的 source/target 服务、Planner Hook 编排、转发 Tool、永久防重状态）与**自动转发**是两条独立触发源，硬合并成一条会在「掷骰绕过内容查看」与「Tool 调用需要授权凭据」之间产生语义纠缠。

## Decision

转发域双路径并存，共享状态、分道发送：

1. **自动转发**：`chat.receive.before_process` Hook 内同步解析**合并转发**与掷骰（纯内存、无 IO），命中后 spawn 后台编舞——延迟 → 协议端直发 `send_group_forward_msg` → **转发内容注入**（目标群）→ **强制发言**（目标群）→ **转发留痕注入**（源群）。
2. **请求转发**：整包搬入原插件的完整链路与 Tool（`request_cross_group_forward`），保留源群强制触发 Planner、**查看资格**、一次性授权、顺序投递与目标群 Planner「自主决定、可沉默」的原有语义。**强制发言**不适用于该路径。
3. 两条路径共用**已投递状态**：自动路径命中并投递成功后登记，请求转发的 Tool 据此拒绝重复；自动路径沉默不登记，请求转发仍可执行。
4. 目标群 Planner 语义按路径分开：自动路径软约束必须说一句，请求路径保持可沉默。

## Considered Options

- **只做自动掷骰、丢弃 Tool 链路**：实现最简，但会砍掉「被请求时转发」这一既有使用习惯（群友 @ 麦麦求转发将不再有效），且原插件的查看资格/授权/顺序投递代码整体作废。
- **只保留原完整链路**：即继续使用 OpenSpec 之外的原插件，自动掷骰与「复用本插件掷骰/注入」的诉求落空。
- **两条路径合并为一条（都掷骰，或都走 Tool）**：都掷骰会使「被请求转发」受随机性影响；都走 Tool 则自动路径需要 LLM 判断，与「纯掷骰自动化」的决策冲突，并重新引入源群 Planner 的长链路延迟。
- **统一两条路径的投递机制为协议端直发**：能消除两套发送代码，但会丢掉请求转发链路的 Host 写库与 `sync_to_maisaka_history` 锚点语义（ADR 0006 的直发模型本就以注入补偿上下文，转发链路不需要再付一次代价）。

## Consequences

- 插件从两个行为域扩为三个，`plugin.py` 之外的转发纯逻辑需要独立层级承载；转发域配置独立成节，`plugin.enabled` 仍是总开关。
- 同一目标群可能被两条路径用不同机制发送（自动=协议端直发，请求=主程序发送链）：两者的上下文呈现依赖各自的注入/同步机制，排查问题时必须先确认是哪条路径。
- 部署 arclinux 时必须停用原 `papaya0481.forward-messages-auto` 插件，否则同一源消息会被两个插件的源群 Planner 触发与 Tool 同时处理，产生重复转发。
- 原插件的永久防重状态（`forward_state.json`）与自动路径的内存防重是两套时间尺度：跨重启的重复只对请求转发链路有防护，自动路径按「消息只在收到时处理一次」的假设只做内存 TTL 防重。

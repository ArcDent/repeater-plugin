# 复读域用独立延迟区间，触发消息注入与延迟并发（取代 ADR 0006 决策 3 的延迟沿用与串行编舞）

ADR 0006 决策 3 的两点被本 ADR 取代：(a) 延迟**沿用** `behavior.delay_min/max`、不新增配置项；(b) 后台编舞里触发消息注入**串在**延迟之前。0006 的其余内容（planner 拦截、协议端直发、两路注入的语义与失败口径）继续有效。

## Context

线上观感问题：从**复读链**达标到复读出现在群里等太久。链路事实（`plugin._send_repeat_decision`）：触发消息注入（`_get_stream_id` + `maisaka.context.append`）被 `await` 在延迟之前，延迟取表情回应域的 `behavior.delay_min/max`（默认 1~6 秒，均值 3.5 秒），之后才协议端直发。用户可见延迟 ≈ 注入 RTT + 1~6 秒 + 发送 RTT。

ADR 0006 刻意共用一套延迟以免新增配置项，但两个行为的自然节奏并不相同：**表情回应**贴慢一点像人在慢慢刷群；复读慢一点就直接错过时机——群友的复读接龙是秒级的，麦麦 6 秒后才跟上时，群里往下聊了。

## Decision

1. **复读域独立延迟**：`repeat` 段新增 `repeat.delay_min_seconds` / `repeat.delay_max_seconds`（float，默认 **0.3 / 1.5**），复读/打断直发只读这一对；表情回应继续用 `behavior.delay_min/max`（默认 1~6 秒不变）。两域延迟从此分开调。
2. **触发消息注入与延迟并发**：`asyncio.gather(触发消息注入, 延迟)`，可见延迟从「注入 RTT + 延迟」变成 `max(注入 RTT, 延迟)`。行为文本注入仍在直发**之后**，因此麦麦聊天历史里「谁发了什么」始终早于「麦麦复读/打断了什么」，顺序不因并发而乱。
3. 编舞的其余语义不变：触发消息注入无条件执行、失败记 warning 继续；直发失败止步、不做行为文本注入；冷却与链终结在出口命中的同步段内已写入，与本任务成败解耦。

## Considered Options

- **直接调小共用的 `behavior.delay_min/max` 默认值**：不新增配置项（保住 ADR 0006 的原意），但表情回应也会变成几乎秒贴，为了一个域的节奏牺牲另一个域的观感。
- **复读完全不延迟（达标即发）**：最快，但与 spec 场景「发送前有自然延迟，不出现决策即发」直接冲突，协议端直发裸秒回的机械感也最强。
- **触发消息注入彻底脱钩（fire-and-forget spawn）**：能把注入 RTT 完全从关键路径摘掉，但两路注入的先后顺序不再有保证，麦麦历史里可能先出现「麦麦复读了草」再出现「谁说了草」。`gather` 的 `max` 上界已经够用，顺序保证更值钱。
- **给注入加超时**：治的是「注入 RTT 异常长」这个尚未观测到的病；RTT 的实际量级还没有实测数据，先不引入第三个时间参数。

## Consequences

- 新增两个配置项，AGENTS.md 里「延迟沿用 `behavior.delay_min/max`，不新增配置项」这条作废；`config_version` 的升级与 ADR 0007 的权重改名合并为同一次（`1.1.0`）。
- config UI 里出现两组延迟字段，label 必须写清作用域（复读侧写「复读发送延迟」，表情回应侧保持「最小/最大延迟」），否则部署者会调错那一组。
- **注入 RTT 的实际量级未实测**：本机 fake SDK 的 `context.append` 立即返回，测不出容器内 RPC 的真实耗时；「注入串在延迟前面必然叠加」是读代码得到的结构事实，不是测量结论。若 RTT 长期大于 1.5 秒，`gather` 的上界会由 RTT 决定，那时才需要回到 fire-and-forget 或注入超时这两个被拒选项。
- `_call_protocol` 每次新建 `aiohttp.ClientSession` 的开销**不动**：同机 HTTP 建连成本远小于注入 RTT 与延迟，换常驻 session 要额外管生命周期（`on_unload` 关闭、热更新时的归属），收益不成比例。这是有意保留的现状，不是漏项。
- 复读延迟缩到 0.3~1.5 秒后，麦麦复读与群友接龙的间隔更近，`repeat.cooldown_seconds`（默认 120 秒）与**链终结**标记成为唯一的刷屏闸门，二者的默认值在观感上比以前更吃重。

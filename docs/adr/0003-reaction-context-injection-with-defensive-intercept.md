# 表情回应上下文感知：防御式拦截通知消息 + 插件自建注入

要让麦麦「知道」群里发生过表情回应（而不是只知道有人贴了、跟风了），需要把表情回应写进 Maisaka 聊天历史。主程序没有任何 `emoji_like`/reaction 处理代码，但 `bot.py` 的 `handle_notice_message` 会让适配器标了 `is_notify=True` 的通知消息照常走完主链（入库、进上下文、参与回复判定）——表情回应会不会被主程序吞进上下文，取决于 snowluma-adapter 转不转发 notice，这一点本机无法验证（ADR 0001 已记录同样的不可验证性）。决定：插件挂 `chat.receive.before_process` Hook（主程序已内置、`allow_abort=True`）做**防御式拦截**——识别到表情回应形态的通知消息就打日志并 abort 掉，这条日志同时就是「适配器到底转不转发」的线上答案；表情回应进上下文只走插件自己的**自建注入**（`maisaka.context.append`，SDK 已暴露）这一条路，不押注任何观察不到的形态。

拦截与注入都由新配置 `context.enabled`（默认关）统一控制：开启即注入 + 拦截，关闭则两不干预，保持「实验性功能整块试、整块关」。

## Considered Options

- **只做加法不拦截**：若适配器也在转发 notice，麦麦上下文里会出现两份表情回应记录（一份适配器原始形态、一份插件去重聚合后的），污染历史且无法消除——因为插件改不动主程序的处理路径。
- **只拦截不注入**：表情回应从麦麦的感知里完全消失，违背需求 2/3。
- **依赖主程序原生支持表情回应**：主程序 1.2.0 无此规划，周期不可控。
- **等 SDK 补通知事件通道**：同 ADR 0001，改上游不可控。

## 注入形态与去重（随本 ADR 一并固定）

- **独立注入**：每条**注入消息**是一条独立上下文消息，可见文本「谁给什么贴了什么」，`source_kind=reaction`，`message_id` 存被回应消息 ID。不合并进被回应消息——后者大概率已不在上下文窗口，定位回填不可靠。
- **去重窗口**：键（回应者，被回应消息，表情 ID）在 TTL 内只注入一次（防协议端重复上报与贴-取消-再贴），默认 3600s 可配。
- **聚合窗口**：同一被回应消息同一表情的多条回应（不同回应者）在窗口内汇入一条注入消息（可见文本列出各回应者），窗口到期 flush；防表情风暴撑爆上下文，另配注入上限兜底。
- **麦麦自己的回应完全同路注入**：不构成循环——注入不产生新上报，只有上报才触发行为。
- **机器人显示名来源链**：优先主程序暴露的 `config.get("bot.nickname")`（官方配置 `bot.nickname`，默认「麦麦」）→ 插件配置项兜底 → 再取不到则不写入名字。不依赖协议端 `get_login_info` 的 QQ 昵称，因为 QQ 昵称与机器人名是两回事。

## Consequences

- `chat.receive.before_process` 的拦截只对「插件认得的表情回应通知形态」生效，认不出仍放行并打日志——拦截逻辑必须与解析层共用同一份形态判定，避免漏拦或误拦普通消息。
- Hook 是声明式的：`context.enabled` 关掉时插件不再订阅该 Hook，主链完全不受影响（Hook 注册在插件加载时按配置决定）。
- 注入消息的时间戳由主程序在调用时刻取 `datetime.now()`，故聚合窗口内的注入时间会比事件发生晚至多一个聚合窗口；这是可接受的已知行为。
- 主程序启动恢复上下文时会跳过 `is_notify` 消息（`_restore_recent_context_from_db`），但**不会**跳过插件的注入消息（`source_kind=reaction` 的 `SessionBackedMessage`）——重启后注入消息可能从主程序消息库恢复，与插件内存去重表不同步，极端情况会出现少量重复注入。已知行为，实验功能可接受。

# 自动转发改在摘要就绪后触发，发送用 before_process 字节快照

## Context

v0.6.0（ADR 0009 / 0010）上线后暴露四个问题：可配置项太少（没有「掷骰后是直发还是交给 LLM 决定」的模式选择）；**转出的转发消息图片丢失**；**目标群模型上下文里没有转发内容**；配置项需要全中文带注释。

诊断证据（只读核查生产日志 / prompt dump / 消息库 + 主程序与 SnowLuma 源码）：

1. **目标群模型不知道麦麦转发了什么**（生产实锤）：2026-09-26 15:17 那次自动转发后，目标群 planner 的 prompt dump 里确有注入文案，但内容是插件自有的**有损段摘要**——图片→`[图片]`、表情→`[表情]`、嵌套转发→`[嵌套转发]`、reply 段丢弃、800 字截断。23:19:46 麦麦在目标群回复「**欸 我转发什么啦**」；15:20 群友仍在问「为啥小小有时候会转发聊天记录」。
2. **图片丢失无法回溯到具体样本**：9/18 至今自动路径仅成功投递 3 次（均在 9/26，且都不含图），9/18–9/23 的日志已被轮换删除。用户报告收端看到 `[图片]` 占位文本——中文 `[图片]` 只可能来自插件 `SEGMENT_PLACEHOLDERS` 兜底，但 before_process 时点 adapter 已把字节下载进内存，静态复刻显示 `binary_data_base64` 齐全、插件转换输出正确。根因呈多候选状态（请求路径 / 早期投递 / 特定图源），**新时机约束使「字节从哪来」成为必须先于实现决断的问题**。
3. **主程序处理时序**（`bot.py receive_message`）：`before_process` hook → `message.process()` → `after_process` hook → 入库 → 注册 Maisaka 上下文。**before_process 时点主程序尚未处理消息**，`processed_plain_text` 不存在、图片无描述。
4. **处理后内存字节被丢弃**（`message.py process_image_component`）：`component.content = "[图片：desc]"` 且 `component.binary_data = b""`。延迟触发越多，越只能靠 DB 按 hash 恢复字节——全量扫描 9/18 至今 4286 个转发内媒体段：**121 个（2.8%）按 hash 取不回字节**，839 个（19.6%）连描述都是空的。
5. **描述回填不进消息本体**：识图描述异步构建，只由 Maisaka `chat_history_refresher` 在每轮 planner 前刷新**内存历史**；消息入库后 `raw_content` 永不更新。首见图的描述在 `get_by_id` 里永远拿不到——「轮询等描述填满」对 19.6% 的候选永远不成立。
6. **垃圾媒体引用可拖垮整包**：`_media_segment` 的引用回落把段内 `data`（处理后已是中文描述文本）当文件引用发出，SnowLuma `loadBinarySource` 会 `statSync` 失败抛异常，**整条 `send_group_forward_msg` 失败**。

用户口径（阶段一澄清）：掷骰命中后两种模式——直接转发，或交给**目标群** Planner 依据内容决定是否转发；转发时机改到**转发卡片完整内容摘要生成以后**；掷骰也推迟；等不到就绪的候选记 warning 放弃；取不回字节的媒体整节点丢弃；配置加模式与两路径开关、全中文。

## Decision

**自动转发**的触发拆成「同步段门禁 + 快照」与「摘要就绪后的决策编舞」两段：

1. **同步段**（`before_process` observe）：形态门禁 → **源群**门禁 → **转发防重** mark → **转发源消息快照**（原始段 + 内存字节，不可变）→ spawn 后台编排。不做掷骰、不写冷却。防重 mark 保持在 spawn 之前的同步原子段内，防自我循环语义不变。
2. **摘要就绪**：后台轮询 `ctx.message.get_by_id`，消息已入库且 `processed_plain_text` 非空即就绪；`forward.summary_timeout_seconds` 兜底，超时记 warning 放弃本次。**不等识图描述回填**——异步描述只进 Maisaka 内存历史、消息本体永不更新，首见图占 19.6%，等待不可观测。
3. **就绪后编舞**：逐**目标群**掷骰（**转发权重**）→ 命中写**源群**/**目标群**冷却 → 延迟 → 可用性校验 → 协议端直发 → **转发内容注入** → **转发留痕注入** → **强制发言**。发送一律用**快照**的原始段与字节，不经 DB 恢复，图片 100% 保全（adapter 下载失败或超限被主程序预先丢弃的除外）。
4. **富摘要注入**：目标群注入文案、源群留痕、**强制发言** intent 的材料从插件自有段摘要改为主程序 `processed_plain_text`。首见图降级 `[图片]` 占位（与现状持平，但覆盖从「全部占位」降为「约两成占位」）。
5. **模式选择**：`forward.mode = direct | planner`。`direct` 维持现语义（命中即直发）；`planner` 命中后不直发，把富摘要交给**目标群** Planner 决策「转发 / 不转发」，据结果走同一套投递编舞。**转发权重**对两个模式都生效（先掷骰再决策）；**强制发言**只适用于实际发生投递时。
6. **媒体兜底**：快照段中不可发送的媒体，所在**转发节点**整条丢弃；全部节点落空则放弃本次投递。`_media_segment` 引用回落收紧：仅 `http(s)://` / `base64://` / 文件路径形态当文件引用，否则文本占位——杜绝垃圾 file 引用（请求路径同样受益）。
7. **路径开关**：`forward.auto_enabled` / `forward.request_enabled` 分别控制两条路径，`forward.enabled` 仍是转发域总闸（与 `plugin.enabled` 合取）。
8. **配置全中文**：新增字段一律中文 `label` / `hint`，`config.toml` 同步中文注释（用户要求 webui 可读性）。

## Considered Options

- **保持 before_process 掷骰、只推迟投递**：现有 spec 30 个场景零改动，但用户明确要求时机含决策本身；且 planner 模式本就须等摘要才能给 LLM 材料。未采纳。
- **after_process 单 hook + 从 DB 取段与摘要**：逻辑最简，但 after_process 时内存字节已清空，只能走 DB 按 hash 恢复（2.8% 取不回，用户已观测过图片丢失）。未采纳。
- **等识图描述填满再算就绪**：对 19.6% 首见图永远不成立，会把候选全拖满超时。未采纳（修订后方案）。

## Consequences

- 转发域从「一个 hook 同步段完成全部决策」变为「同步段门禁 + 快照，后台等就绪后决策」；`forwards/` 需新增快照数据结构与就绪轮询（逻辑层可单测），`plugin.py` 编排相应调整。
- **时序副作用**：掷骰推迟后，冷却在命中后才写入；就绪等待窗口（通常亚秒级）内到达的新**合并转发**会各自通过门禁并独立掷骰，「同步段原子写冷却压制突发」的强度下降。防重 mark 仍在同步段，语义不变。
- 注入文案质量取决于主程序识图覆盖率；首见图仍占位。要 100% 描述覆盖需主程序改动（入库后回填或暴露识图完成信号），超出插件边界。
- planner 模式让转发域出现第三个行为面（自动直发 / 请求转发 / 决策转发），spec 需新增模式相关场景；注入文案与掷骰时序相关的既有 scenario 需 MODIFIED，防重 / 冷却 / 门禁 / 直发机制主体不变。
- 群名乱码（`<$ÿĀ\x11\x10>柴犬的新窝`，DB 内 `group_name` 本身损坏，协议端/适配器编码问题）会继续污染注入与 intent 文案；插件侧应在注入前清洗控制字符（实现期处理，不改变本 ADR 决策）。
